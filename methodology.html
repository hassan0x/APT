01
01 · Initial Access T1566.002
Spearphishing via Trusted Cloud Storage
  • Themed phishing email sent to a targeted employee — invoice, shipment, or HR lure
  • Payload hosted on a legitimate cloud storage provider to bypass URL reputation checks
  • No attacker infrastructure in email headers — sender domain is clean
  • Link delivers a ZIP or compressed archive to the victim machine
  • Legitimate domain hosting defeats most email gateway and proxy blocklists
Delivery vector: https://[legitimate-cloud-storage]/[lure-filename].zip → no malicious infrastructure in delivery path
02
02 · Execution T1204.002
Masqueraded EXE — Icon Spoofing + Extension Hiding
  • Archive contains a real decoy document + an EXE disguised with a document icon
  • Windows hides known extensions by default — victim sees two identical-looking files
  • Victim double-clicks the fake document thinking it is legitimate
  • Downloader runs silently in background — no visible window or UAC prompt
  • Decoy document may open simultaneously to avoid suspicion
Lure.zip Document.pdf <- real decoy, opens normally Document_v2.pdf <- actually Document_v2.pdf.exe // Windows shows both as "PDF Document" — victim cannot tell them apart
03
03 · Staging T1105
Download Signed Legitimate Binary + Malicious DLL
  • Downloader contacts attacker-controlled cloud bucket for second-stage payload
  • Downloads a legitimate binary signed by a trusted vendor — used as the sideload host
  • Downloads the malicious DLL that uses the same name the signed binary imports
  • Both files saved to the same directory (AppData, ProgramData, or Temp)
  • Same-folder placement is a prerequisite for DLL sideloading to succeed
  • Malicious DLL often embeds additional resources (drivers, shellcode) in its .rsrc section
Staged to: %APPDATA%\[random_folder]\ LegitApp.exe <- signed by trusted vendor, clean TargetDLL.dll <- malicious, embeds drivers + shellcode
04
04 · DLL Sideloading T1574.002
Malicious Code Runs Inside a Signed Trusted Process
  • Downloader launches the legitimate signed binary
  • Windows DLL search order: application directory is searched BEFORE System32
  • Signed binary loads the attacker-placed DLL automatically from the same folder
  • Malicious DllMain() executes — the attack now runs inside a trusted signed process
  • EDR sees a signed binary loading a DLL from its own folder — low suspicion
  • Process parent/child chain, code signing, and module provenance all appear legitimate
LegitApp.exe asks Windows: "where is TargetDLL.dll?" Windows checks: application directory first -> FOUND Loads TargetDLL.dll into process memory automatically DllMain() executes -> attack begins inside trusted process
>>> KERNEL BOUNDARY     RING 3 → RING 0
Everything below this line executes with kernel-level privileges — EDR user-mode hooks cannot interfere
05
05 · BYOVD — Bring Your Own Vulnerable Driver T1562.001 RING 0
EDR Killed from Ring 0 via Vulnerable Signed Driver
  • Malicious DLL extracts one or more .sys drivers embedded in its resources section
  • Writes each driver to disk (Temp, ProgramData, or System32\drivers)
  • Loads driver via SCM: CreateService(SERVICE_KERNEL_DRIVER) + StartService()
  • Opens a device handle to the driver and sends an IOCTL with the EDR process PID
  • Vulnerable driver executes ZwTerminateProcess(EDR_PID) from Ring 0 — cannot be blocked
  • Multiple drivers act as fallback chain — if one is on the blocklist, try the next
  • Target: any security process running as PPL — kernel call bypasses PPL protection entirely
DeviceIoControl( hVulnDriver, IOCTL_KILL_PROCESS, &edr_pid, sizeof(DWORD), NULL, 0, NULL, NULL ); // ZwTerminateProcess(EDR) executes from Ring 0 // PPL protection, self-protection callbacks — all bypassed

06 · Defense Evasion T1562.001
NTDLL Unhooking — Removing EDR's User-Mode Visibility
  • EDR injects JMP hooks at the entry of NTDLL.dll syscall stubs to intercept all calls
  • Attacker reads a clean, unmodified copy of ntdll.dll directly from disk
  • Overwrites the hooked in-memory bytes with the original instruction bytes from the disk copy
  • All JMP hooks removed — subsequent syscalls reach the kernel with no EDR interception
  • Combined with BYOVD: kernel-level EDR dead + user-mode hooks stripped = full blind spot
// Before unhooking — EDR intercepts every syscall: NtCreateProcess: JMP edr_hook -> EDR inspects + logs // After unhooking — original bytes restored from disk: NtCreateProcess: MOV R10, RCX MOV EAX, syscall_num SYSCALL <- goes direct to kernel RET <- EDR sees nothing

07 · C2 Communication + Process Injection T1055.003
Thread-Context Hijacking into a Trusted System Process
  • DLL fetches final shellcode payload from C2 server over encrypted channel
  • Shellcode is never written to disk — lives entirely in memory
  • Locates a long-running trusted system process (e.g. svchost.exe) as injection target
  • Allocates RWX memory region inside target via VirtualAllocEx()
  • Writes shellcode into the allocated region via WriteProcessMemory()
  • Suspends an existing thread, redirects its RIP to the shellcode, then resumes it
  • No new thread created — execution flows through an existing thread with a legitimate call stack origin
OpenProcess(PROCESS_ALL_ACCESS, target_pid) VirtualAllocEx(hProc, NULL, size, MEM_COMMIT, PAGE_EXECUTE_READWRITE) WriteProcessMemory(hProc, pRemote, shellcode, size) OpenThread(THREAD_ALL_ACCESS, thread_id) SuspendThread(hThread) GetThreadContext(hThread, &ctx) ctx.Rip = (DWORD64)pRemote // hijack RIP to shellcode SetThreadContext(hThread, &ctx) ResumeThread(hThread) // payload now executing

08 · Persistence — Dual Watchdog Architecture T1053.005
Two Independent Recovery Layers Keep the Implant Alive
  • Watchdog 1 (internal): background thread monitors the injected shellcode's memory address
  • If shellcode is evicted or target process dies → re-fetches from C2 and re-injects
  • Watchdog 2 (external): script polls for the loader process every few seconds
  • If loader process is killed → immediately relaunches it
  • Scheduled Task monitors the script itself → fires on boot + periodic trigger
  • Killing the loader evicts the DLL from memory, but the task respawns it on next boot

All three layers must be removed simultaneously to fully evict the implant

09 · Remote Access — Final Payload RAT / Implant
Persistent C2 — Full Control, No File on Disk
  • Shellcode runs inside a trusted system process — no dedicated malware process visible
  • Network traffic blends with legitimate traffic from the host process
  • Full remote shell: execute arbitrary commands, read output, control the system
  • File operations: upload additional tooling, exfiltrate documents and credentials
  • Recon: user, groups, network config, running processes, installed software
  • Modular: operator can push additional capabilities on demand (keylogger, screenshots, pivoting)
Implant location: shellcode inside legitimate system process Network traffic: encrypted C2 protocol, blends with host process Disk footprint: loader binary + DLL only (shellcode is fileless) Persistence: dual watchdog + scheduled task survives reboot
END STATE — Full persistent access, all defenses bypassed

>> CORRECT INCIDENT RESPONSE ORDER
1Block the C2 IP/domain at the network firewall first — cuts off operator control and re-fetch capability
2Delete the Scheduled Task — prevents the watchdog from being recreated on next boot/trigger
3Kill the watchdog script process and delete the script file from disk
4Kill the loader process — this evicts the sideloaded DLL and watchdog thread from memory
5Delete all dropped files from disk: vulnerable drivers (.sys), the DLL, the signed loader binary
6Reboot — fully unloads any remaining kernel drivers, clears all in-memory shellcode
